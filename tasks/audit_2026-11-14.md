## 1. AI Chatbot (highest priority)

**What is solid (code and tests only):** the prompt builder marks missing values "not recorded" and rule 18 forbids inventing personal facts; the last 8 real messages go in as history; local redirects and errors are kept out of the history; the answer is sanitized by guardrails; errors become an error reply, never AI text; the conversation is saved on the device after each turn; the screen shows a loading status and a retry. Context sent: profile, goal, workouts, nutrition (unknown calories and protein flagged), recovery, steps, recent cardio.

### CHAT-1 AI backend dependency (High, blocks demo if it fails; UNVERIFIED)
- **Screen:** AI Coach (`lib/screens/ai_coach_screen.dart`).
- **Issue:** a release build has no developer key. `AIConfig.isConfigured` is true only when the build has the Supabase URL and anon key (`--dart-define-from-file=.env`) and a user is signed in; every request then goes through the Supabase `ai-proxy` Edge Function, which must be deployed with the Gemini secret and a daily quota.
- **Reproduce:** install the APK, open AI Coach signed out, then signed in, then in airplane mode, then ask "How many calories did I log today?".
- **Expected:** signed out: a clear "sign in" notice; signed in: an answer using your real logged data, or "not recorded" when data is missing; offline: a retryable error.
- **Actual:** unknown. I did not call the proxy (live AI calls are off limits in this project).
- **Likely cause if it fails:** proxy not deployed, secret or quota missing, or the build lacked `.env`.
- **Fix and dependencies:** you check the proxy and a signed-in answer on the phone first. A backup for the presentation: a few pre-tested prompts and screenshots. A repeat offline test is also needed.

### CHAT-2 Misleading "attach" options (Medium)
- **Screen:** attachment sheet in AI Coach.
- **Issue:** "Workout History Data", "Nutrition & Food Logs", "Progress & Metric Summary" say "Attach ..." but only send a fixed sentence. The app already adds your data to every prompt.
- **Expected vs actual:** a user thinks data is attached; in fact the label promises something the button does not do.
- **Fix:** rename to "Ask about my workouts / meals / progress" (text change; no new screen).

### CHAT-3 Fake "context reloaded" message (Low)
- **Issue:** `_refreshContext` waits 400 ms and then says "Training & nutrition context reloaded!" regardless of what happened.
- **Fix:** remove the delay and show the message only after the reload finishes, or drop it.

### CHAT-4 Not yet tested for the demo (UNVERIFIED)
Conversation history after closing and reopening the app, behaviour when asked about data the app lacks (heart rate with no watch, steps), error and retry display, and a long answer. Part of the phone checklist.

## 5. Steps counter and activity

### STEP-1 No sensor-based step counting (Critical, blocks demo)
- **Screens:** Dashboard steps card, Cardio/Activity screen, Health dashboard.
- **Issue:** `StepTrackingService` only stores steps that the user types (Cardio screen: "Log Today's Steps" and quick-add buttons). No pedometer or step-counter sensor is read. The `health` plugin can read steps from Health Connect (Health Dashboard), but those are not saved into the same store, so the dashboard card and the Health Dashboard can show different numbers. `ACTIVITY_RECOGNITION` is declared in the manifest but nothing uses it.
- **Reproduce:** walk 200 steps, open the dashboard.
- **Expected:** the daily count rises as you walk and survives a restart; resets at midnight.
- **Actual:** stays 0 until typed.
- **Fix and dependencies (needs your decision):**
  - A) Add a step-counter package (new dependency, needs your approval) reading the phone's step sensor with the Activity Recognition permission, storing a per-day baseline so restarts and midnight work.
  - B) No new dependency: read today's steps from Health Connect into the same store. Works only if the phone's health app writes steps there (Google Fit, Samsung Health, a watch).
  - I recommend A for a live demo; B is the fallback. Both need device testing.

### STEP-2 Invented weekly history (High, blocks demo; invented data)
- **Screen:** weekly activity chart and activity score.
- **Issue:** `StepTrackingService.getWeeklyHistory` fills any day without a record with `6000 + ((i * 731) % 4500)` steps ("mock variation for realistic charts"). The activity score also reads this history.
- **Expected:** days without data show as no data.
- **Fix:** return no-data days (zero or absent), and let the score and charts treat them as unknown. Small code change; chart appearance for "no data" days may change, which I will show first.

### STEP-3 Day reset and persistence (UNVERIFIED)
Records are keyed by date, so a new day starts at zero by design; to be tested across midnight and an app restart on the phone. Distance uses 0.762 m/step in one place and 0.75 m in another (Low).

## 6. Heart rate and other fitness features

### HR-1 Fake fallback health data (Critical, invented data)
- **Where:** `HealthSyncService` falls back to `LocalHealthProvider`, which returns fixed values (8,450 steps, 420 kcal, 68 bpm average heart rate, 7.5 h sleep, 42 active minutes, plus a fake 7-day history). `FitnessProvider.syncHealthData` uses it to set the recovery score and training state. Reached from the wearable connection card and device connect.
- **Expected:** with no data source, no values and no recovery score from invented numbers.
- **Fix:** remove the fake fallback (return nothing), let the recovery logic treat it as missing.

### HR-2 Invented defaults on the Health dashboard (High)
- **Screen:** Health dashboard: subtitle `Resting: ${restingHeartRate ?? 64} bpm` and `${deepSleepMinutes ?? 90}m deep sleep`.
- **Expected:** "--" when not available.
- **Fix:** one-line each; no layout change.

### HR-3 Mock wearable on the Recovery screen (Critical, invented data)
- **Screen:** Recovery dashboard. The selected platform starts as `WearablePlatform.mock`; the Garmin and Fitbit chips are also local mock classes with fixed values (for example resting HR 54, HRV 78).
- **Expected:** only Health Connect data, or an honest "connect a data source" state.
- **Fix:** remove the mock, Garmin and Fitbit options from the screen or label them clearly as demo data. Visual change (chips and empty state): mockup first.

### HR-4 No live heart-rate display (Medium)
The phone has no heart-rate sensor. Real readings exist only if a watch or band syncs to Health Connect; the polling stream exists but no screen shows a live value. Do not show a number without a source. **Fix:** an empty state that says "No heart-rate source connected" with a connect button, and a latest-reading card when data exists. A Bluetooth heart-rate strap would need a new package (your approval); not recommended before Wednesday.

### HR-5 Health Connect on the demo phone (UNVERIFIED)
Health Connect must be installed (Android 13 and below) and permissions granted. The app's permission request, the denied state and the unavailable state have tests but were not tried on a phone.

### HR-6 Showcase Mode (Medium)
Showcase Mode replaces profile, nutrition, community and health values with sample data (`HealthMetric.sample()`, sample meals). If it is on during the demo, those figures are not measurements. Decision needed: keep it for the community only (see COM-1) and keep health and nutrition real.
